# velvet-turnip

Сборщик погодных и морских данных для планирования береговой рыбалки на леврека (сибаса)
на побережье Алания — Махмутлар — Газипаша (Турция).

GitHub Actions каждые 3 часа (`17 */3 * * *` UTC) запускает `collector/collect.py`. Скрипт берёт
прогноз и морские данные из Open-Meteo, считает производные значения и коммитит:

| Файл | Что внутри |
|---|---|
| `data/latest.json` | Компактный результат для чтения моделью: точки, Луна, устья, окна ловли с оценкой (`windows`), почасовая лента оценок (`timeline`), температура воды, предупреждения |
| `data/summary.md` | Сводка по-русски: топ-3 окна на 7 дней, таблица окон на 3 дня, состояние устьев |
| `data/raw/latest_raw.json` | Сырые ответы API последнего запуска (перезаписывается) |
| `data/history/YYYY-MM-DD.json` | Снимок `latest.json` на каждый день (последний запуск дня перезаписывает файл) |

Чтение для потребителя:

- https://raw.githubusercontent.com/ruslan-fayzullin/velvet-turnip/main/data/latest.json
- https://raw.githubusercontent.com/ruslan-fayzullin/velvet-turnip/main/data/summary.md

### Как поменять точки

1. Отредактируйте `config/points.json`:
   - `coastal[]`: прибрежная точка и `marine_id` её морской пары;
   - `marine[]`: морская точка;
   - `rivers[].catchment[]`: точки водосбора, поле `zone` (`below_dam` / `above_dam` / `middle` / `upper`);
   - `rivers[].nearby_coastal`: к каким прибрежным точкам относится устье (влияет на `score`).
2. Обновите `config/points.geojson`, чтобы карта совпадала с конфигом.
3. Проверьте локально: `python3 collector/collect.py` (Python 3.12, без зависимостей).

## Как считается

Время везде `Europe/Istanbul`, ветер в м/с, волна в метрах, осадки в мм.

### Осадки водосбора и `mouth_state`

Для каждого водотока берутся средние почасовые осадки по его точкам водосбора. По ним считаются
суммы за прошедшие 24 и 48 ч, прогноз на 24 и 48 ч, час пика за последние 72 ч (час с ≥ 0,1 мм) и
сколько часов прошло с пика. Правила проверяются по порядку:

| Состояние | Условие |
|---|---|
| `dry_or_low` | за 48 ч < 10 мм (или пика не было) |
| `flood_now` | пик < 12 ч назад и за 24 ч ≥ 25 мм |
| `prime` | с пика прошло 12–36 ч (и за 48 ч ≥ 10 мм) |
| `fading` | с пика прошло 36–72 ч |
| `rising` | остаток: пик < 12 ч назад, но за 24 ч < 25 мм (вода прибывает) |

Для Dim Çayı дополнительно выводятся осадки отдельно ниже и выше плотины. Сток частично
регулируется плотиной Dim Barajı, поэтому дождь выше неё доходит до устья с задержкой и сглаженно.

История начинается с `past_days=3`: при `past_days=2` она начиналась бы с 00:00 позавчера, а это
меньше 72 ч, нужных для поиска пика.

### Окна ловли (`windows`)

Сутки делятся на четыре окна:

| Окно (`kind`) | `light` | Интервал |
|---|---|---|
| `рассвет` | `twilight` | от восхода −1 ч до восхода +1,5 ч |
| `день` | `day` | лучший 3-часовой отрезок между концом рассветного и началом закатного окна |
| `закат` | `twilight` | от захода −1,5 ч до захода +0,5 ч |
| `ночь` | `night` | лучший 3-часовой отрезок от конца заката до начала следующего рассвета; относится к дате вечера |

День и ночь длинные, поэтому для них перебираются все 3-часовые отрезки периода (с шагом 1 ч, не раньше
текущего часа) и берётся лучший: максимальная оценка, при равенстве — без грозы, потом более ранний. У таких
окон есть дополнительные поля:

- `period_start`, `period_end` — границы всего периода (дня или ночи);
- `period_thunder_hours` — сколько отрезков периода с грозой. Если выбранный отрезок чистый, а в другие
  часы этого периода грозы, оценка снижается на 1: модель ошибается со временем гроз на часы;
- `period_precip_mm` — осадки за весь период.

Во всех окнах есть `light`, `cloud_mean_pct` (средняя облачность) и `moonlight` — эффективный лунный свет
0..1: освещённость диска × доля чистого неба, 0, если Луна под горизонтом. Высоту Луны считает
`moon_altitude()` (упрощённая модель, как в suncalc, точность ~1°).

Окна считаются на 7 дней для всех прибрежных точек. Кроме того, в каждом окне: средний ветер и его румб
(векторное среднее, 16 румбов), максимальный порыв, флаг `onshore` (ветер с 90°–270°, т.е. SE–S–SW–W),
средняя и максимальная волна, период, осадки, флаг `thunder` (`weather_code` 95–99 или CAPE > 1000 в окне
или в соседние ±2 ч), тренд давления за 6 ч до окна. Состояние ближних устьев считается на момент окна,
с учётом прогноза осадков.

### Почасовая лента (`timeline`)

`timeline` — оценка каждого часа на 7 дней вперёд по каждой прибрежной точке. Формат по колонкам:
`timeline.<point_id>` — объект с массивами одинаковой длины `time`, `light`, `score`, `no_go`, `thunder`,
`wind_ms`, `wind_dir`, `onshore`, `wave_m`, `precip_mm`, `cloud_pct`, `moonlight`; i-й элемент каждого
массива относится к часу `time[i]`. Оценка часа считается тем же `score_window()`, что и окна. Часы за
горизонтом прогноза, где нет ни ветра, ни волны, пропускаются.

### `score` (1–5) и `reasons`

Логика собрана в функции `score_window()` в `collector/collect.py`, пороги по времени суток — в `LIGHT_MODS`:

1. База 2.
2. `thunder` → оценка 1 и `no_go: true`.
3. Средняя волна 0,4–1,2 м → +1.
4. `onshore` при ветре 3–10 м/с → +1.
5. Ветер с суши (N, NNE, NE) сильнее 4 м/с → −1.
6. Ближнее устье в состоянии `prime` → +1.
7. Время суток:
   - сумерки (`twilight`, рассвет и закат) — базовый случай, без поправок;
   - день: −1 (у берега леврек держится хуже, чем в сумерки); облачность > 70 % или осадки > 0,2 мм → +1
     (свет приглушён, день возвращается к уровню сумерек, но не выше); облачность < 40 % и волна < 0,3 м → ещё −1
     (ясно и тихо, прозрачная вода);
   - ночь: решает освещённость. `moonlight` < 0,2 (тёмная ночь) → +1, > 0,7 (яркая Луна при ясном небе) → −1.
8. Волна < 0,2 м → оценка не выше 2.
9. Максимальная волна > 1,8 м → флаг `dangerous_on_rocks: true`.

Итог ограничивается диапазоном 1–5. Каждое срабатывание правила пишется строкой в `reasons`.

## Надёжность

- Сетевые ошибки повторяются с backoff 2/4/8/16 с.
- Если Forecast или Marine API не ответил совсем, скрипт завершается с ненулевым кодом. Workflow
  падает, и GitHub присылает письмо.
- Частичные пропуски (null у одной точки) не роняют скрипт, а попадают в `latest.json` → `warnings`.
- Правило 60 дней: в публичном репозитории GitHub отключает scheduled workflows, если в репозитории
  60 дней нет активности. Документация не говорит, считаются ли активностью коммиты самого workflow.
  Поэтому последний шаг workflow вызывает REST API
  `PUT /repos/{owner}/{repo}/actions/workflows/collect.yml/enable` с `GITHUB_TOKEN` (`actions: write`).
  Повторное включение сбрасывает счётчик неактивности, и пустые «keepalive»-коммиты не нужны.
